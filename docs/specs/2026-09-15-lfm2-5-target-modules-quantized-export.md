# LFM2.5 `target_modules` + quantized export

> unsloth-cli trains full-coverage LoRA adapters for LFM2.5 (short-conv blocks included, via an explicit `target_modules` key with an lfm2 preset) and exports any adapter as merged-16bit, merged-4bit, quantized GGUF, or AWQ W4A16, so the same adapter runs on a Jetson Orin Nano (llama.cpp), a Jetson Thor or DGX Spark (vLLM), or lobes' hand lane
> instruction: Verify by reading docs/tested.md: rows for LFM2.5-1.2B-Base train, gguf, awq, merged-16bit

## Audience

- AgentCulture mesh agents and their operators producing adapters on a DGX Spark, plus three deployment targets: Jetson Orin series incl. Nano 8 GB (llama.cpp/Ollama GGUF, or vLLM AWQ W4A16), Jetson Thor and DGX Spark (vLLM NVFP4 preferred, or bf16 + LoRA via lobes hand)
  - instruction: README and docs/fine-tuning.md name all three targets and which export format each consumes

## Before → After

- Before: Today sloth train silently adapts only what Unsloth auto-detects (LFM2 conv blocks excluded), sloth export only copies a PEFT adapter directory, and nothing produced by this repo can run on a Jetson or as a quantized vLLM model
- After: An operator trains an LFM2.5-1.2B-Base adapter with `target_modules` = "preset:lfm2", then runs sloth export --format gguf --quant `q4_k_m` for an Orin Nano or --format awq for Thor/Spark vLLM, each producing a self-contained model directory plus export.json, with every step honouring --json, --dry-run and error:/hint:
  - instruction: docs/tested.md carries one real Spark row per format (gguf, awq, merged-16bit) and one LFM2.5-1.2B-Base train row

## Why it matters

- Adapters are only useful where they run: lobes hand needs loadable LoRA dirs, edge Jetsons need a single quantized file, and the same Spark that trains should be able to serve a W4A16 build without a second toolchain

## Decisions

- Ship as two PRs, each with a real Spark run recorded in docs/tested.md: (1) `target_modules` key + preset:lfm2 + the LFM2 hint + dry-run/metadata surfacing + chat-template preflight, validated with a real LFM2.5-1.2B-Base train; (2) the four container-backed export formats (merged-16bit, merged-4bit, gguf, awq) + llama.cpp cache mount + llmcompressor in the dep layer + export.json, validated with real gguf, awq and merged-16bit runs
- merged-4bit stays in the format set (low cost: one more `save_method` on the same container path); no format support is dropped
- `target_modules` is never auto-selected from the model id; when an LFM2/LFM2.5 model id is trained without `target_modules`, sloth train prints a stderr hint pointing at the lfm2 preset and proceeds with Unsloth's auto-detect. Explicit config over guessing
- AWQ / W4A16 export is in scope alongside GGUF: Jetson Orin, Jetson Thor and DGX Spark are all target consumers of the quantized artifacts
- Quant format per target: Spark and Jetson Thor (Blackwell) get NVFP4 as the preferred quantization; the Jetson Orin series gets GGUF or AWQ W4A16
- export.json lands in both places: next to the exported artifacts and as an exports index in the source adapter dir
- sloth eval accepts a merged or quantized model directory (--model DIR) in addition to --adapter, so the same eval suite scores bf16 vs gguf vs awq vs nvfp4

## Hard questions

- Does vLLM's LoRA path for Lfm2ForCausalLM accept adapters on conv.`in_proj` / conv.`out_proj` / w2? lobes' frame cites only `packed_modules_mapping` `qkv_proj`, w13, `in_proj` (hand frame line 947); if vLLM rejects `out_proj` or the conv modules, a full-coverage lfm2 adapter fails to load on lobes' hand lane while a Jetson GGUF (merged) is unaffected — must be measured on the Spark before the preset is fixed (resolved: measured live on the Spark: vLLM nightly loads and applies a conv-covering LFM2.5 LoRA adapter (q/k/v/`out_proj`, conv in/`out_proj`, w1/w2/w3); preset:lfm2 resolves to the regex string)
- Does the llama.cpp tag/prebuilt that `unsloth_zoo`.`llama_cpp` fetches include lfm2 in `convert_hf_to_gguf.py`? Liquid publishes official LFM2.5 GGUFs so upstream supports it, but the tag Unsloth pins (`UNSLOTH_LLAMA_TAG`, `llama_cpp.py`:710) is unknown; no llama.cpp checkout exists on this host to inspect (resolved: measured live: Unsloth's prebuilt llama.cpp b10909 (arm64) converts and quantizes LFM2.5 to `Q4_K_M` and runs it; pin `UNSLOTH_LLAMA_TAG` and mount $HOME/.unsloth)
- Does llm-compressor's AWQModifier handle Lfm2ForCausalLM (short-conv `in_proj`/`out_proj` layers and w1/w2/w3 naming) out of the box, or does LFM2 need an explicit ignore/mapping list? Qwen3 is a safe first target; LFM2 awq needs its own Spark run (resolved: measured live: AWQ W4A16 works via llmcompressor 0.11.0 + compressed-tensors 0.16.0 + a torch.accelerator.`get_memory_info` shim, pipeline=basic, custom LFM2 per-layer mappings with no `v_proj`->`out_proj` pair; NVFP4 works on both 0.11 (shim) and 0.10.0.3 (no shim))
